### 2.3 轴序与间距为什么不影响结论（核对员的论证，复核确认）

导出的 d 是体素坐标、分量次序 (z, y, x) 的拉回位移；u 是毫米、分量次序 (x, y, z)。设 S(x) = H⁻¹P(x − o)，其中 P 把 (x, y, z) 倒成 (z, y, x)，H = diag(h_z, h_y, h_x)，o 是原点。

- **精确算术下**：体素映射 ψ(p) = p + d(p) 满足 ψ = S ∘ Φ_u ∘ S⁻¹，因为 d(p) = H⁻¹P u(S⁻¹p)。S 把网格格点映到格点、把轴对齐单元映到轴对齐单元，Q1 张量积空间在这种变换下不变，所以三线性插值与这个仿射换元可交换。于是 det Dψ(p) = det(H⁻¹P) · det DΦ_u · det(PH) = det DΦ_u(S⁻¹p)：J > 0 在两种坐标下逐点等价。原点平移不影响 J。
- **浮点上的限定**（修订 1，I4）：存盘的是 d = fl(u/h)，BL1 认证的是 fl(h·d)。两者与同一个实数场逐位对应，要求乘除都精确，也就是 h = 1 或 h 是 2 的幂。h 不是这样时 d 与 fl(h·d) 都有舍入，逐位对应就断了，上面的等价只对各自存盘的数组分别成立。LPBA40 与 OASIS 的 h 都恰为 1.0（2.2、2.4），所以逐位对应成立：h = 1 时 d 与 u 只差分量次序，除以 1.0 与乘以 1.0 都精确。

由此，OASIS 一侧：
- BL1 认证的 u = fl(h·d) = d（h = 1，逐位，只差分量次序），**就是导出的 d**。BL1 50/50 通过、六面为 0，就是"导出的 d 的三线性插值在每个闭单元上 J > 0"的证书读数；这个结论在 BL1 路线的依赖（第 5.1 节）下成立。
- result.md 没有记逐对的 u_equals_h_d_bitwise 与 state_hash_matches_cert_json，本核对也没读，所以"决定配置证书认证的 final.npz 的 u 与导出的 d 逐位对应"这一项在 OASIS 一侧仍是没核到。对上一条结论它不是必需的。

## 3. (b) 浮点前提 × 三条路径

### 3.1 binary64（没有 float32、混合精度或 x87 扩展精度）

- 入口：certify_map 先把 u 转成自有的 C 序 float64 副本（feasibility.py:402）；certify_jacobian_only 同样（cert_eval.py:53）。Interval 的端点在 `__post_init__` 里强制为 float64（interval.py:36–41），NumPy 的 _fallback_arrays 用的就是 Interval。fallback_arrays 只在 float64 输入时走编译内核（compiled_fallback.py:186–188）。
- 编译产物（v1_codegen.out）：
  - 所有内核签名都是 float64 数组；
  - 优化后的 IR 里，float、half、x86_fp80、fp128 运算都是 0，fptrunc 与 fpext 都是 0；
  - 汇编里 x87 运算 0，ss/ps 单精度运算与转换 0；
  - 复核员用 objdump 扫真实目标码（1.1），结果相同；

### 3.2 舍入：就近偶数（修订 1，I1：拆成"运行时是否成立"与"本路径是否需要"）

**运行时是否成立：三条路径一样，只有间接证据。**
- 静态：bayesreg/、experiments/、scripts/ 和 eb808be 的 jd_curl/ 里都没有 fesetround、set_flush_denormal、mxcsr 之类的调用。numba 的 fastmath 在所有证书内核上都是 False（targetoptions 读数）。汇编里没有 ldmxcsr、fldcw、fldenv、fxrstor 这类写控制字的指令。
- 今天的探针（v1_fpstate.out，场景 A、B）：所有探到的线程里，MXCSR 的 RC = 0，x87 RC = 0，fegetround = 0（FE_TONEAREST）。这些线程是主线程、新线程、jd-curl-scan、jd-curl-edge-hull 和新 ThreadPoolExecutor 线程，也包括导入 torch 等库并跑过 torch 与 BLAS 的 CPU 运算之后。复核员在真实的配置 C 与 BL1 调用里，于每个算判定的位置读到同样的结果（复核 1.3）。
- 运行内自检的覆盖（场景 D；复核 1.3 在真实调用里复现）：jd_curl 的两个自检分别是 interval.py:16–28 与 compiled_enclosure.py:83–89，舍入一项都是 `1 + 2⁻⁵³ == 1`。
  - 在 FE_UPWARD 下它们返回 False，证书失败关闭；
  - 在 **FE_DOWNWARD 与 FE_TOWARDZERO 下都返回 True**，证书照常跑完，所有算判定的线程都处在该模式里（复核 1.3）。
  - 所以运行内的自检只排除向上舍入。运行当时是就近舍入，三条路径的证据都只是静态核对加今天的探针。

**本路径是否需要就近舍入。**
- (i)(iii) **不需要**。这是**本线的补充论证**，不是 [P1] 的结论：论文里 Lemma lem:outward 只对就近舍入陈述。复核员确认了这条论证（复核第 2 节第 2 条、次要 3）。**修订 2（小核对 I2 取 (b)，decision_log 8bd09d9b）：下面三条只是分析，未登记为命题、未证明，稿件不用。** 稿件只写"正性不依赖 test (ii) 的先验界"；要把这条写进稿件，得先登记命题、写证明、数值脚本入库、做独立复核，MICCAI 稿不做。
  - Lemma lem:outward 的结论是"↓ẑ < z < ↑ẑ 或 z = ẑ"。论证只用到 ẑ 取 z 两侧相邻的两个浮点数之一，任何忠实舍入都满足，IEEE 的四种舍入方向都是忠实舍入。
  - Lemma lem:hoisting 的证明只用到舍入单调，在四种方向下都成立。
  - 定向舍入下上溢可能给出有限的 ±DBL_MAX，而不是 ±∞。随后的外推会把越界那一端推成 ±∞，被有限性检查拦下，判为未决。代码里的检查是 `_nr_outward` 的 ok 旗（compiled_enclosure.py:162–165）与 Interval.__post_init__（interval.py:36–41）。
  - 数值上，复核员在向下、向零、向上三种模式下各做 306 个单元，(i)(iii) 0 违反，编译版与 NumPy 版的 (iii) 在四种模式下都逐位相同（复核 1.4）。
- (ii) **需要**。附录 C 的先验界按 |ε| ≤ u = 2⁻⁵³ 推导；定向舍入下单步误差界翻倍。附录 C remark (ii) 说 Step 1 的条目误差界在对抗单元上已取到 0.974，所以按原文写的常数在定向舍入下的最坏情形可以失效。复核员测到的总比值 ≤ 4.5e−3（向下舍入）只是经验，不能拿来把这一格升级（次要 6）。**所以 (ii) × 就近舍入记"有条件"**：条件是运行时确实是就近舍入，静态与探针都支持这一点，但运行内的自检不能直接证明。

### 3.3 渐进下溢（FTZ、DAZ 都关）

- 今天的探针（场景 A、B）：所有探到的线程里 FTZ = DAZ = False（MXCSR 0x1fa0/0x1fa2，只是状态位不同）。导入 torch、MKL、OpenBLAS、llvmlite、cudart/cudnn 的共享库（场景 B 共载入 195 个 .so）、跑过 torch 的 float32/float64 矩阵乘、conv3d、linalg.solve 与 NumPy BLAS 之后，状态不变。
- 正控制：
  - 场景 C：torch.set_flush_denormal(True) 后，主线程 MXCSR 变成 0x9fe2（FTZ、DAZ 都开）。此时两个自检都返回 False，certify_map 返回 uncertain / unsupported_arithmetic，即失败关闭；之后新建的线程继承 FTZ/DAZ，之前建的线程不变（Linux 线程创建时继承创建者的浮点环境，本机实测如此，POSIX 的 pthread_create 也这样规定）。
  - 一个外向舍入区间乘积在 FTZ 下**包不住**精确值：(−3e−160)·(5e−160) = −1.5e−319 被冲成 −0，外推后下端只到 −5e−324；渐进下溢下正确包住。这说明这条前提对 (i)(iii) 是实打实的。
  - 复核员另用 fesetenv 设 FTZ+DAZ，以及 **FTZ 单独、DAZ 单独**，两个自检在设置线程和它新建的子线程里都返回 False，失败关闭（复核 1.3，修订 1 次要 5）。
- **运行内证据**（记录读数）：
  - 决定配置（LPBA40 17 对）：reason 都是 positive_enclosure_cover，不是 unsupported_arithmetic，所以每次证书调用时主线程的 NumPy 自检通过了。n_fast_cells > 0：parallel_margins 先在 jd-curl-edge-hull 线程里跑编译版自检，不通过就抛 ArithmeticUncertain，那样就不会有 (i) 证出的单元，所以那个线程的编译版自检也通过了。这两个线程在修复、复核、评测三个进程里都不是 FTZ/DAZ，修复进程里是导入 torch 并初始化 CUDA 之后。
  - **BL1**（LPBA40 17/17、OASIS 50/50；修订 1，I3 (b)(e)）："BL1 通过"本身就说明，那次调用里主线程的 NumPy 自检通过了，因为 certify_jacobian_only 在进入各路径之前先跑它，不通过就返回 unsupported_arithmetic（cert_eval.py:60–61），这一条 LPBA40 17/17、OASIS 50/50 都适用；BL1 的 n_fast > 0 说明主线程的编译版自检也通过了，这一条只对 LPBA40 读到（17/17，n_fast 6,726,892–6,925,649），OASIS 的 BL1 n_fast 没读。BL1 的编译版自检在主线程跑，不在 edge-hull 线程（1.2）。这排除了评测进程主线程在那次调用时的 FTZ、DAZ 与向上舍入。
- 自检不在 jd-curl-scan、jd-curl-cert 工作线程里跑。jd-curl-cert 每次调用由主线程新建，继承主线程在同一次调用里刚通过自检的状态。jd-curl-scan 池是常驻的，环境是创建时从创建者（主线程或 edge-hull 线程）继承来的，之后没有代码改 MXCSR（静态核对）；对它，运行内没有直接证据（修订 1，I3 (d)）。这记作设计上的薄弱处，不算前提不成立（第 5 节第 2 条）。

### 3.4 不收缩（没有 FMA）

- IR 与汇编（v1_codegen.out）：
  - (i)(ii)(iii) 的所有证书内核，加上 SoA、单单元版本与域检查，快速数学标志行、llvm.fma/fmuladd 内建、vfmadd/vfmsub/vfnmadd/vfnmsub 指令都是 **0**。
  - 复核员用 objdump 扫真实目标码，独立得到同样结果（复核 1.1）。还补查了核对稿漏掉的 `_chunk_hoisted_margins` **只读数组签名**：运行里 u 冻结时用的就是它，LPBA40 的缓存里两个签名各有一条。两个签名的可执行段逐字节相同，FMA 为 0（修订 1 次要 1）。
  - 正控制：同一台机器上 a*b+c 用 fastmath=True 或 {'contract'} 编译，各出 1 条 vfmadd，结果与 CPython 不同（0x1p−54 对 0）；fastmath=False 时 0 条，结果相同。这说明本机的 LLVM 在得到许可时会生成 FMA，而证书内核没有得到这个许可。
- 能收缩的地方在哪里（IR 数据流：fadd/fsub 的操作数直接来自 fmul）：
  - (i) `_chunk_hoisted_margins`：**0 处**。每个乘积先进 fcmp/select（min/max），再经 `call @numba_nextafter`，然后才参与加减，结构上就没有可收缩的组合。nextafter 调用 84 处，与源码逐运算数出来的数一样：9 个元素 × 3 次外推 × 2 个端点 = 54，行列式 14 次 × 2 = 28，"− δ" 1 次 × 2 = 2。IR 摘录：`%.9511 = fmul double …` → `fcmp ole` / `select` → `@numba_nextafter`。
  - (ii) 预筛内核：**27 处**。例如 `%.1221 = fmul double …; %.1223 = fadd double %.1221, 0.0`，对应源码的 `acc += term`、余子式、Bernstein 变换。这些地方都没有 contract 标志。汇编里是分开的 vmulsd/vaddsd：临时目录里该内核 .s 的第 317–318 行是 `vmulsd -56(%rcx), %xmm11, %xmm11`，后接 `vaddsd %xmm7, %xmm11, %xmm12`。临时文件没入库，sha256 前缀见 v1_codegen.out。
  - (iii) 编译回退内核：**63 处**，按源码都在只作诊断的 float64 样本部分（compiled_fallback.py:134–173）。它算的 sampled_min_jd 只进记录，_classify 的判定用区间 p（feasibility.py:305）。区间部分的乘积都经 min/max 与 nextafter。这个归属是读源码得出的，没有在 IR 里逐条追。
  - (iii) 的 NumPy 实现（BL1 用它）：每个初等运算是一次单独的 ufunc 调用，中间有数组落地，不可能融合。
- NumPy 实测：multiply 后接 add，2000/2000 与 CPython 不收缩结果逐位相同，而 FMA 结果在 2000/2000 上不同（v1_numerics.out 末段）。
- BLAS：证书判定路径不调 BLAS。在 feasibility、interval、compiled_enclosure、soa_enclosure、certificate_prescreen、compiled_fallback、thread_chunks、interpolation、validation、work_control、grid 里，dot、einsum、matmul、tensordot、linalg、`@` 都是 0 处。cell_q1 的系数表逐元素构造（cell_q1.py:48–59），`@` 只在 Q1 算子的作用方法里（cell_q1.py:72、104、120），certify_map 不调。geometry.determinant 只用于 NumPy 样本诊断（feasibility.py:276–292），而且是逐元素乘后 np.sum。
- 缓存（修订 1 次要 2；复核 1.2）：
  - LPBA40 修复进程的 jit_cache 键含这些：jd_curl 全部源码；各核模块的代码对象，包括每个 dispatcher 的 targetoptions（fastmath 在内）；Python、NumPy、numba、llvmlite 的版本；numba 的代码生成配置（OPT、LOOP_VECTORIZE、SLP_VECTORIZE、ENABLE_AVX、CPU_NAME、CPU_FEATURES 等）。Numba 自己的索引键另加签名与目标（triple、CPU 名、特性）。所以开了 fastmath 或 contract 的编译，或者别的版本、别的 CPU 编出的条目，都载入不进来。

### 3.5 不重结合（含并行归约）

- 所有证书内核的 IR 里 reassoc 与 fast 标志都是 0，也没有 vector.reduce 内建。
- 判定路径上的浮点和都是顺序求和，就是 (ii) 的 `acc += term`（Appendix C 第 (a) 步规定的顺序），没有并行或向量化的浮点求和。预筛内核汇编里打包运算 0 条。正控制：一个求和循环用 fastmath=True 编译，出 10 条 vaddpd，结果与顺序和不同；用 fastmath=False 编译，0 条，结果相同。

### 3.6 外向舍入（对照论文一 §A.3 Lemma "outward" 与 §4.4）

论文的要求（arXiv 源 sections/04_certificate.tex §4.4，A_proofs.tex §A.3）是：每个初等运算（+ − × ÷）先就近舍入，再把下端点移到朝 −∞ 的下一个可表示数，上端点移到朝 +∞ 的下一个；模板常数 0、1、½、2 精确；非有限中间结果、除数区间含 0 或前提违反时，相关单元记为未决。

- (i) 用的 libm 内核：每次运算后两端各调一次 glibc nextafter。numba 把 np.nextafter 降为 `@numba_nextafter`，即 numba/_helperlib.c:213 的 `return nextafter(a, b)`，复核员看到它的反汇编是一条 `jmp nextafter@plt`。调用数与源码逐运算的数一致（84）。原始边差先就近舍入、取最小最大、再外推，是论文 Lemma "Hoisting" 的写法。"− δ" 在 δ = 0 时也外推一次，偏保守。任一步非有限就置旗，整块不预证（feasibility.py:650–651），交给后面的路径。
- (i) 的 SoA 内核（没用上）：用整数位步 _up/_dn 代替 nextafter。396/396 个单元上与 libm 版逐位相同。
- (iii)：
  - 编译内核（配置 C）在每次运算后 `_nr_outward`。对精确的乘法（乘 2、乘 ½、乘二进有理权）也照样外推，偏保守。
  - NumPy 的 Interval（BL1 的 (iii)，以及两种配置的细分）每个运算之后 `outward` 一次，用 np.nextafter（interval.py:51–94）；split_bernstein 每一步都是外推的区间运算。端点非有限或倒置时抛 ArithmeticUncertain，记为未决。
  - 只除以正的点 h，没有除以含 0 区间的情形。
  - 复核员在 6 个场景下核了 213 个值（含 ±0、次正规数、DBL_MIN、±1e308），NumPy 与 Numba 两种 nextafter 都与按位步进的参照 0 不符（复核 1.4 末段）。
- 写法是 **nextafter**，不是另加 ulp 余量，与 §4.4 一致。
- (ii) 不做外向舍入，用先验界：
  - 表格前提（Appendix C：D = fl(1/h_j)·c，c 为 0 或 2 的幂，非零元正规）在 h = (1,1,1) 与 (.7, 1.3, 1.1) 上逐项精确成立，见 v1_numerics.out 头部。h = 1 时元素就是 {0, ±¼, ±½, ±1}。
  - 判定写法 fl(min β̂ − B̂) > 0 与代码一致：certificate_prescreen.py:120 写 `out = low − bound`，feasibility.py:679–680 写 `margin_pre > 0`。
  - 396/396 个单元上 |β̂ − β| ≤ B̂，最大比值 2.2e−3。

- (ii)：内核与 CPython 不收缩复刻逐位相同（396/396）；FMA 收缩版有 344/396 在比特上不同（次正规两类 0/52，因为那里 F 的元素都精确）；|β̂ − β| ≤ B̂（396/396）；out ≤ min β（396/396）；out > 0 时真值为正。
- (iii)：编译回退与 NumPy 区间代码逐位相同（396/396）；27 个点上的精确 J 与精确 Bernstein 系数都落在计算出的区间里（396/396）；两层 NumPy 细分（每层沿三个轴各切一次）都包住精确的子盒系数（396/396）。
- 判定：认证 ⇒ 真值为正；不可行 ⇒ 真值非正；配置 C 与 BL1 的单元下界 ≤ 152 个点上的精确 J（396/396）。

贴着阈值认证的最小下界：(i) 2.8e−17，(ii) 4.4e−17，全图 6.9e−17–1.7e−16，这些情形的真值都为正。

读法（修订 1 次要 7）：逐位相等是旁证，只覆盖跑到的输入与分支，也看不出乘积本来就精确之处的收缩（那种收缩本来无害）。不收缩的决定性证据是机器码里 FMA 为 0（3.4）：核对员查了现编的，复核员另查了现编的与 LPBA40 缓存载入的。

### 5.1 BL1 路线：输出的正性不依赖 (ii)（修订 1，I3；"也不依赖就近舍入"只作分析，见 (f)）

论证：LPBA40 17/17 的 BL1 在同一份字节上通过（state_hash 相同），最小下界与决定配置相同；OASIS 50/50 的 BL1 在导出的 d 换成的 u = fl(h·d) 上通过（h = 1，所以就是 d），六面为 0。由 Thm 4.4 中 test (i) 与 (iii) 的那部分（Lemma lem:outward、lem:edgehull、lem:hoisting 与 Bernstein 包含），每个输出位移的三线性插值在每个闭单元上 J > 0。

这个论证依赖下面几条，逐条写明：
- (a) **BL1 的 (iii) 是 NumPy 的 `feasibility._fallback_arrays`**，在 jd-curl-cert 线程里算，不是编译版 `_fallback_kernel`。所以这条路线上 (iii) 的证据是：3.4 的 NumPy 一段（不可能融合）；3.7 的"编译与 NumPy 逐位相同、都包住精确值"（396/396）；复核 1.4 在四种舍入方向下也核了 NumPy 版。
- (b) **BL1 的编译版自检在主线程跑**：certify_jacobian_only 不传 margins_future，`_certify_map_parallel` 在调用线程里直接调 parallel_margins（复核 1.3 实测）。第 3.3 节"n_fast > 0 ⇒ edge-hull 线程自检通过"只对决定配置成立；对 BL1，n_fast > 0 说明主线程的编译版自检通过了。
- (c) **评测进程现编、不用缓存**，它的 numba/llvmlite 版本没有记录：评测记录只记了 Python 与 NumPy 的版本。"该进程的机器码与今天检查的相同"是〔推断〕，依据是同一个 conda 环境（项目规则：不建新环境、不自行安装），加上同版本、同主机的编译是确定的（复核 1.2 缓存对现编的逐字节相同是旁证）。
- (d) **jd-curl-scan 工作线程的浮点环境靠继承**：运行内没有直接证据，静态核对表明没有代码改 MXCSR（3.3）。jd-curl-cert 每次调用由主线程新建。
